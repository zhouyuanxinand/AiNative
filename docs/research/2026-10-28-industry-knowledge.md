# 工业研发 AI Native：知识治理、本体与证据闭环调研

调研日期：2026-10-28。范围：连接器制造企业四平台的全局职责、知识循环，以及在既有 taskbook 引擎不变的条件下受控补齐工程依据。本笔记是方案依据，不是源码已实现能力清单，也不是行业普遍实践统计。

任务给定的四平台边界：K-box 管合格知识、数据、画像及来源引用；本体管概念、关系、属性、规则、动作、标准结构和源映射；Workspace 管专家、技能、专家团的版本、评测、发布与授权；研发管理管项目业务事实、审签和成果采用。taskbook 初次生成保留既有 LLM 路由 source_id → copy_exact；生成后已有 review revision API 支持人工修订当前 DOCX 并复核，不要求每次补齐都重生成。本子任务对修订与复核路径做了定向源码核验，见第 6 节；其余平台边界来自任务上下文，不代表完整源码审计。

## 1. 可直接用于全局定位的结论

**建议以“合格证据—明确语义—受控能力—业务决定”形成闭环，四个平台分别承担不同权威职责。** 本体解释工程对象和约束，K-box 证明来源与可用性，Workspace 约束 AI 能做什么，研发管理记录项目最终采用什么以及谁承担决定责任。这是结合任务边界的设计推论；不能把 Palantir 或 Siemens 的产品模块直接等同于本项目四平台。

官方资料提供三个可迁移的依据：

- OWL 可表达术语、关系及逻辑蕴含；缺失事实不等于假，也不会凭空产生工程实测真值。SHACL 则对给定数据执行约束校验并产出结果，两者用途不同。[OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)；[SHACL](https://www.w3.org/TR/shacl/)（访问：2026-10-28）。
- Palantir 文档明确描述由 AI 形成提案、操作人员完善并决定，以及以动作权限控制人或代理在何种条件下执行变更的模式。[Palantir Platform overview](https://www.palantir.com/docs/foundry/platform-overview/overview)（访问：2026-10-28）。
- PROV 提供实体、活动、代理及派生、归属、修订、失效关系，可表达“结论用了什么证据、经过什么活动、由谁负责”。具体批准状态机和撤回处理政策仍须本项目定义。[PROV-O](https://www.w3.org/TR/prov-o/)（访问：2026-10-28）。

## 3. 四平台职责与业务权威边界（设计建议）

| 平台 | 对外负责的对象 | 允许交给其他平台的内容 | 不应据此获得的权威 |
| --- | --- | --- | --- |
| K-box | 合格知识、数据、画像及其来源引用、版本、适用范围、权限和可用状态 | 可引用的证据条目与精确位置；经批准的知识包；撤回和替代信息 | 原件权威保留在来源系统；入库或被引用不改变来源权威，也不等于适用当前项目 |
| 本体平台 | 工程概念、关系、属性、单位语义、标准结构、约束、动作契约及源字段映射 | 固定版本的语义包、约束包、映射包、校验结果、变更影响范围 | 不补造未知参数、不替代实测、不以概念推理代替工程签字 |
| Workspace | 专家/技能/专家团定义、版本、输入输出契约、可调用工具、评测、发布与授权 | 已发布授权能力、能力版本和依赖说明；能力的执行结果可通过 Runtime 供业务引用 | 资源生命周期管理不意味着持有所有业务 Runtime 记录的权威；专家团意见不构成项目批准，发布也不等于对所有项目授权 |
| 研发管理 | 需求、任务、项目参数、评审、变更、验证结果、签批与成果采用的业务记录 | 有上下文的执行委托；批准后的项目事实；可申请沉淀的经验与反馈 | 项目通过的特例不能自动升级成全公司的通用规范 |

本体动作契约描述“何种对象在何种条件下可以怎样变化”；Workspace 管理可用能力的资源生命周期；Runtime 承载技术执行及相应记录；研发管理持有项目委托关联、业务审签和成果采用；K-box 治理可复用知识及来源引用。来源系统保留原件权威。四平台可共享对象标识与事件，但不需要复制四份相互竞争的业务真值。该划分参考 S1 的数据/逻辑/动作及 S4 的跨系统溯源思想，具体划分由本项目需求决定。

## 4. 知识循环：候选和批准是两个门槛（设计建议）

知识循环建议为：

原始材料/项目结果 → K-box 来源登记与权限检查 → 抽取或人工整理候选 → 本体映射与约束校验 → 领域专家核验 → K-box 发布合格知识版本 → 研发项目委托已发布授权的能力检索适用知识并形成提案 → 人工核验、审签与采用 → 验证实际结果 → 反馈成为新候选。

Workspace 的能力评测、发布与授权是独立的资源生命周期。知识发布后，已发布且获授权的能力可按其契约检索现有合格知识；只有知识或语义变化影响能力适用范围、固定依赖或评测假设时，才触发相应影响评估、复测，必要时发布新能力版本。不能要求每次知识发布都重新发布全部能力。

应区分两个状态轴：

| 状态轴 | 状态示例 | 决定者 |
| --- | --- | --- |
| 知识可复用状态 | 候选、待核验、存在冲突、已发布、已取代、已撤回 | K-box 知识责任人及对应领域审核者 |
| 当前项目采用状态 | 待评审、采纳、拒绝、需重新评估；是否允许“附条件采纳”由企业制度另行确定 | 研发项目的授权审批人；不默认新增审批门 |

“已发布知识”仍可能不适用当前项目；项目“采纳”也不会自动成为全局合格知识。发布前至少核对原始出处、原文位置、适用产品/材料/环境/版本、权限、冲突、必要的工程审查记录。这里的门槛是我们建议的治理制度，不能声称为 OWL、PROV 或 GraphRAG 自带能力。依据：S1 提案模式、S3 校验机制、S4 溯源模型。

## 5. 语义版本、证据版本与撤回影响（设计建议）

建议每次可审阅的运行/成果固定一组版本引用，而非只留一个“最新知识库”名称：

| 引用 | 应能回答的问题 |
| --- | --- |
| 项目事实快照/基线 | 采用哪版需求、产品配置、试验条件和项目批准事实？ |
| 证据条目与原件版本 | 用了哪份文件、哪一页/条款/表格/数据记录？是否有内容摘要校验值、许可和适用期限？ |
| 本体、约束、源映射版本 | 当时概念如何解释、怎样换算单位或识别字段、用哪套规则检查？ |
| 技能/专家/专家团发布版本 | 哪个能力、工具配置和授权范围生成了提案？ |
| 运行、文档修订与采用决定 | 谁执行、哪一修订版/段落锚点被人工修改、谁核验和决定、为何采纳或拒绝？新增候选证据如何关联仍待契约建设。 |

采用新标准或新映射时，先明确受影响对象和字段，再决定重新校验、重新运行或重新审签。旧成果保留当时引用与决定，不静默改成新版本。

撤回链建议：证据责任人撤回或标记失效 → 保留原版本和原因 → 停止其在新运行中的适用资格 → 按“证据—映射/知识包—能力评测/运行—成果—项目采用”依赖关系生成影响清单 → 通知授权责任人重新评估 → 记录维持、替换、补验证或变更决定。对于受撤回证据影响的索引/缓存，更新检索资格并按依赖需要重建；不要仅在原文件上加标签而继续返回旧摘要。

S4 支持表达派生、修订和失效关系，但“撤回后自动找影响、触发审签”是待实现的应用能力；不能从采用 PROV 自动推导出它已存在。

## 6. 保留现有生成与修订流程的任务书补齐

### 6.1 已有能力：修订当前文档，再独立复核

以下为 2026-10-28 定向源码核验事实，不是拟新增能力：

| 已有能力 | 核验位置 | 能力边界 |
| --- | --- | --- |
| 保存人工确认的正文操作 | [review_controller.py](<D:/桌面/研发管理平台-主包 1021/AiNative/basic-service/app/src/controller/review_controller.py:147>)：`POST /{jid}/revisions` 校验 `expected_revision_id`，应用操作并保存新版 DOCX | 当前版本已变化则拒绝旧版本修改；保存修订不要求重跑生成引擎 |
| 按段落锚点修改、插入、删除 | [review_document.py](<D:/桌面/研发管理平台-主包 1021/AiNative/basic-service/app/src/service/jonhon_taskbook/review_document.py:375>)：支持 `replace_text`、`insert_paragraph`、`delete_paragraph`，使用 `element_id` 定位并另存 DOCX | 需满足现有段落可编辑性和操作校验；不能假设所有锚点均允许修改 |
| 保留修订链与差异 | [review_store.py](<D:/桌面/研发管理平台-主包 1021/AiNative/basic-service/app/src/service/jonhon_taskbook/review_store.py:276>)：保存 `parent_id`、操作者、原因、SHA-256 与 changes | 文档修订字段不等于新增本体证据引用契约 |
| 对指定修订版执行 recheck | [review_controller.py](<D:/桌面/研发管理平台-主包 1021/AiNative/basic-service/app/src/controller/review_controller.py:185>)；[review_checks.py](<D:/桌面/研发管理平台-主包 1021/AiNative/basic-service/app/src/service/jonhon_taskbook/review_checks.py:145>) | 检查【人工填写】及既有生成证据等；技术复核与工程审签分别进行 |
| 基于本次生成账本重算 coverage | [review_checks.py](<D:/桌面/研发管理平台-主包 1021/AiNative/basic-service/app/src/service/jonhon_taskbook/review_checks.py:36>)：读取 `evidence_coverage_ledger`，对当前 DOCX 及已有 sidecar 重算覆盖 | 不能据此宣称后来检索到的 K-box/本体候选证据已进入 coverage |

既有 `source_id → copy_exact` 是初次生成流程；人工确认后通过现有 revision API 修改当前文档是应优先复用的补齐路径。不能把初次生成约束扩张为“每个待办补齐都必须修改输入并整包重生成”。

### 6.2 优先路径：围绕生成后的待办锚点辅助补齐（接入建议）

下表的本体/K-box/Workspace 联动是建议能力；第 7、8 步复用已存在的修订和复核接口。能力执行结果通过 Runtime 提供，项目委托、人工确认及采用关系由研发管理关联。

| 步骤 | 执行与产物 | 放行条件 |
| --- | --- | --- |
| 1. 定位待办 | 在当前任务书修订版定位【人工填写】、未决问题和相关段落 | 带项目、`revision_id`、待办及 `element_id`；保存时以 `expected_revision_id` 防止覆盖新版本 |
| 2. 分类原因 | 专家或受控技能提出“缺证据/有冲突/模板占位/须工程判断”及依据 | 允许多标签；原因不明就保留未决，不能全部归为缺知识 |
| 3. 查询语义 | 本体解释字段定义、单位、适用对象、试验条件、源映射及约束 | 提议保留语义/规则/映射版本；版本消费契约待建设 |
| 4. 检索证据 | K-box 在权限和适用范围内返回有来源引用的候选依据 | 显示原文位置、版本和适用范围；候选不自动计入原有 coverage |
| 5. 形成修改候选 | 已发布授权能力将建议文字、证据、差异、限制和待验证项关联到待办锚点 | 保留冲突；不凭模型置信度判定真值，不自动写入当前文档 |
| 6. 人工工程确认 | 工程师核验候选并确认具体修改；需要时补试验、计算、项目决定或转模板责任人 | 确认适用性与修改内容；未解决则保持待办 |
| 7. 修订当前文档 | 复用既有 revision API，以 `expected_revision_id` 和支持的段落操作生成新版 DOCX | 保留现有修订链与差异记录；补齐本身不强制重跑生成引擎 |
| 8. 对新版 recheck | 调用既有修订版检查接口，核对未决项及既有生成证据覆盖 | 新增证据未进入现有账本的限制单独说明；检查通过不等于新增依据已验证 |
| 9. 业务审签与采用 | 研发管理基于修订文档、人工确认依据和未决项走授权审签 | 业务批准后进入相应成果基线；修订保存、recheck 和工程批准分别记录 |
| 10. 反馈沉淀 | 将有复用价值的补齐结果申请作为 K-box 知识候选 | 经知识责任人审核适用范围后才发布，不自动“自我学习成真” |

**尚待建设的接入契约**：新增候选证据的不可变版本引用；候选—待办—修订前后段落—人工确认记录的关联；权限与适用范围的消费规则；是否及如何使新增依据参与后续复核。现有 revision API 和 coverage 账本不能被描述为已经完成这些接入。实施前须另行明确数据契约；本笔记没有新增接口或改动代码。

### 6.3 例外路径：输入纠错或明确要求整包重生成

只有原输入/源材料错误，或业务明确要求整包重新生成时，才准备经确认的新不可变输入包，保留与旧包的版本关系，再重跑原有 `source_id → copy_exact`。新生成文档仍进入现有 review、修订、recheck 与业务审签。正常的本体辅助补齐使用 6.2 的当前文档修订路径，不将输入包重建设为前置条件。

### 6.4 四类缺口的不同处置

- **缺证据**：检索、联系证据责任人、补取试验或外部正式文件；找不到就保留缺口。
- **有冲突**：呈现冲突来源、版本、测试条件和适用范围；由授权工程师判定适用性，不让模型选“更像正确”的数值。
- **模板占位**：正常项目内容由工程责任人按当前有效模板填写；只有模板定义、结构或格式错误才转模板责任人修订。不能将所有占位都解释为本体缺失或模板错误。
- **须工程判断**：模型可整理备选方案、历史依据和权衡，最终工程选择与签批形成新的项目事实；它不一定适合作为通用知识。

例如“接触电阻”待办，建议本体解释参数含义、单位、产品配置和试验条件；K-box 返回有出处的候选材料；已发布授权能力展示条件差异并给出修改候选；工程师确认后通过既有 revision API 修改对应段落，再复核与审签。没有正式材料时不编造阈值，也不把该候选自动记为原账本已覆盖。本例是流程示意，不是连接器规范条文。

## 7. 运行与角色页面的最小表达（设计建议）

页面应围绕上述责任分工组织，而非四个平台都做一个聊天入口。

| 平台/角色 | 页面关注对象 | 必须可见的判断依据与动作 |
| --- | --- | --- |
| K-box / 知识管理员、领域审核者 | 证据入库队列、知识候选、知识版本、撤回影响 | 原文位置、版本、适用范围、权限、核验意见；批准发布、退回、取代、撤回 |
| 本体 / 领域架构师、语义维护者 | 概念与标准结构、源映射、约束、语义版本差异 | 字段定义、单位与条件、映射来源、校验结果、受影响消费者；提交与批准语义变更 |
| Workspace / 能力开发者、评测者、发布者 | 专家/技能/专家团、评测、发布、授权、运行追踪 | 输入输出契约、知识与语义依赖、失败案例、工具权限、发布版本；评测、发布、授权、停用 |
| 研发管理 / 项目工程师、项目负责人、审签者 | 项目事实、AI 委托、补齐任务、成果比较、审签、成果基线 | 项目上下文、候选与正式结果区分、逐项证据、未决项、采用理由；补证、核验、签批、变更 |

同一补齐事项可跨四个平台被引用，但研发管理应给工程师一个连续的“定位当前文档待办—查看依据—人工确认—修订—recheck—审签”的项目视图；不要求用户手工在四个平台复制内容。修订与 recheck 复用现有能力，跨平台证据关联是接入建议，须另行明确契约。
