# 需求确认实际结果的显式采用

依据：2026-11-06 用户要求初入需求确认时实际结果显示 `--`；只有采纳 AI 推荐或完成澄清并明确采用后才有值。

## 处理规则

- 原文指标继续保留来源正文，不能通过清空原文来制造未确认状态。
- 实际结果由当前有效的规范建议采纳记录或澄清采用记录确定。初始、建议生成但未采纳、不采纳、澄清仅答复均显示 `--`。
- 无可采纳建议、存在差异、拒绝建议时使用既有“办理澄清”流程；保存答复与采用答复仍为两个动作。
- 移除表格内直接填写实际结果的入口；服务端拒绝新 `manual` 实际值命令，避免绕过澄清。既有本地草稿可查看、复制与清除，不静默丢弃。
- 服务端与前端确认门禁覆盖全部需求；原文非空不代表已确定实际结果。编辑需求正文不会自动确认。
- 保持已固定基线、原文、历史决定和历史澄清记录，不回写或清理用户已有项目。只读历史基线继续显示当时采用值。
- 逐项操作不使其他未改变需求的有效决定失效；来源变化、当前需求修订、建议重建仍沿用版本核对。

## 实施划分

1. 后端收紧 review_requirement、实际结果判定和 check_requirement_reviews，校对澄清采用与跨行版本关系。
2. 前端复用 RequirementDecisionTable、requirementConfirmation 与现有澄清入口，共用实际值判定；沿用 Ant Design 表格、按钮及主题，不引入新弹窗或文字操作流。
3. 更新 UX 合同中与本次要求冲突的历史默认值/人工直接填写规则。
4. 定点验证未采纳、采纳、拒绝、无匹配、答复未采用、采用澄清、旧批次、跨行操作、只读历史及错误恢复；刷新真实项目只读查看，禁止为验证伪造真实采纳。

## 验证范围

- 后端完整受影响需求决定、需求确认、规范审查测试文件；仅按明确依赖扩展，禁止无筛选全量。
- 前端实际结果/确认门禁单元测试，以及受影响需求决定、规范审查和确认恢复浏览器文件。
- TypeScript 与生产构建；浏览器检查初始空值、操作后持久化、桌面和窄屏。
- 未执行新模型调用或全量任务书生成时须在最终说明中明确。
